# UL 1998:2018 — 可编程组件中软件 安全标准

> **类型**: concept
> **创建时间**: 2026-07-30
> **最后更新**: 2026-07-30
> **来源**: [[standards/ul-1998-2018|UL 1998:2018 全文]]

## 摘要

UL 1998 标题为 **Standard for Safety for Software in Programmable Components**（可编程组件中软件安全标准），**Third Edition** 原始日期 **December 18, 2013**；本版包含截至 **September 24, 2018** 的修订，**ANSI 认定日期为 September 21, 2018**[1]。

该标准适用于执行安全相关功能、且其失效可能导致火灾、触电或人身伤害的非联网嵌入式软件（non-networked embedded software）。它是**引用型标准**（reference standard）——仅当被其他产品/部件标准明确引用时才适用（§1.2）[1]。在北美 EVSE 体系中，UL 2202 / UL 2594 / UL 2231 等涉及可编程安全功能（如 CCID 自检、隔离监测逻辑）时即引用本标准要求。

### 适用范围（§1 Scope）

- §1.1 适用于**非联网嵌入式软件**，位于执行安全相关功能的可编程组件中，其失效可能导致火灾、触电或人身伤害[1]
- §1.3 仅处理"由软件控制的产品硬件"所独有的风险
- §1.4 用于**补充**适用产品或部件标准，不作为火灾/触电/伤害风险评估的唯一依据
- §1.5 处理的风险类型包括：需求转换错误、设计错误（错误算法/接口）、编码错误（语法/符号/死循环）、时序错误、微电子内存错误、微电子硬件失效诱发的错误、潜在/用户/IO/量程等仅在特定状态显现的错误、组件完全不执行功能[1]
- §1.7 **不涵盖网络安全**——未授权访问或通过网络攻击的风险由产品标准或其他引用标准（如 UL 2900-1）处理[1]

### 关键术语（§2 Definitions）

- **可编程组件 Programmable Component**（§2.39）：任何可在设计中心、工厂或现场编程的微电子硬件
- **微电子 Microelectronics**（§2.24）：满足以下之一——数字模式 >1000 门、>24 个功能不同的外部电气连接、或功能可重编程（含 ASIC/ROM/RAM/PROM/EPROM/PAL/PLD）
- **关键段 Critical Section**（§2.5）：执行应对或控制风险功能的软件段
- **监督段 Supervisory Section**（§2.52）：控制关键段与非关键段执行的主软件段（如微处理器操作系统）
- **RA 状态 Risks-Addressed State**（§2.45）：所有可合理预见的、与预期使用相关的风险均已被应对、不再有发生可能性的状态
- **OTS 软件 Off-The-Shelf Software**（§2.30）：市场可得、广泛分发、通常无需额外定制的软件（操作系统、运行库、实时执行体等）
- **非联网嵌入式软件**（§2.27）：在单一微处理器/微控制器或同一物理外壳内的微控制器上执行、不依赖外壳外收发数据的嵌入式软件

### 风险分析（§3 Risk Analysis）

- §3.1 须进行风险分析以确定：(a) 风险集合；(b) 软件是否应对了已识别风险
- §3.3 须分析识别软件的**关键、非关键、监督**段
- §3.4 须分析识别可能导致风险的**状态或状态转换**[1]

### 软件设计（§6 Software Design）

- §6.1 软件中的故障**不得**引发导致风险的事件
- §6.2 一旦检出可能导致风险的条件，软件须维持 **RA 状态**
- §6.4 须采用手段识别并响应可能导致风险的状态，例如初始化、fail-safe 与 fault-tolerant 概念、运行时检查、内置测试
- §6.7 所有变量在被任何指令使用前**须赋予初值**（若由工具保证，则该工具确认须含此验证）[1]

### 关键与监督段（§7 Critical and Supervisory Sections）

- §7.1 软件须初始化至文档化的 RA 状态
- §7.2 关键段、监督段须相互隔离，并与非关键段隔离
- §7.5 监督段须在可编程组件运行期间维持对软件执行的控制
- §7.6 一旦检出关键/监督段失效，软件须启动 fail-safe 或 fail-operational 程序
- §7.7 当安全相关功能启动可能导致风险时，除非产品安全标准另行规定，须采用**至少两条指令序列**验证该启动
- §7.10 监督段与关键段软件须驻留于**非易失性内存**（若运行期间转入易失性内存，相关风险须纳入 §3 风险分析）[1]

### 微电子硬件失效措施（§8）

- §8.1 须采用手段应对 §3 风险分析识别的全部微电子硬件失效模式（示例见 Appendix A）
- §8.2 须考虑的物理失效包括：CPU 寄存器/指令译码/程序计数器/寻址与数据通路、中断处理、时钟、非易失/易失内存与寻址、内部数据通路、外部通信与数据/寻址/时序、IO（模拟 IO、D/A、A/D、模拟多路复用）、监测与比较器、ASIC/GAL/PLA/PGA[1]
- §8.4 若可编程组件厂商提供勘误（erratum），须提供证据说明相关错误已被修复/测试/批准分发，或受影响功能未被用于安全相关软件开发

### 接口（§9 Product Interface / §10 User Interfaces）

- §9.1 任何时长的电源中断下，软件须维持文档化的 RA 状态
- §9.3 软件终止时，产品须维持 RA 状态
- §10.4 启动可能导致风险的操作，须由**两个或更多用户响应**触发
- §10.5 来自外部源、执行后可能导致风险的输入命令，未经操作员干预不得启动
- §10.8/§10.9/§10.10 产品安全标准与风险分析要求时，软件须提供用户取消当前操作并返回 RA 状态（取消须单次用户输入，且取消后软件处于 RA 状态）[1]

### 分析与测试（§11）

- §11.1 软件设计与代码分析须证明关键/监督段仅执行预期功能且不导致风险（含分支/函数覆盖、fail-safe/fail-operational 到达 RA 状态、分区完整性、接口一致性）
- §11.2 测试含开发期与发布后测试，须覆盖各决策与函数
- §11.3 除正常使用测试外，须进行**失效模式与应力测试**，用例含越界（out-of-range）、边界条件（boundary）、参数类型不匹配（type mismatched）[1]

### 文档与变更（§12 / §13 / §14）

- §12 须文档化：用户文档、软件计划、风险分析方法与结果、配置管理计划、可编程系统架构、需求规格、软件设计、分析与测试文档
- §13 OTS 软件：须提供名称/版本、供应商、用途、接口规格、已知 bug 列表及验证/认证证据
- §14 参数设置与数据变更、软件补丁**不得**产生或恶化已识别风险；须有程序维护与控制关键/监督段变更以便追溯[1]

### 标识（§15 Identification）

- §15.1 软件须可追溯到存于非易失内存的**唯一标识符**
- §15.2/§15.3 唯一标识符须反映关键/监督段的变更；每次向关键/监督段并入变更或补丁，须分配新唯一标识符[1]

### 附录 A — Software Classes（规范性当产品标准如此声明时）

- **A3.1 Software Class 1**：控制功能以降低设备相关风险可能性（例：洗衣机热切断、门锁）
- **A3.2 Software Class 2**：控制功能以降低**特殊风险**（如爆炸）可能性（例：自动燃烧器控制、无排气热水器热切断）
- **A3.3 除非产品安全标准另行规定，所有软件视为 Class 1**
- **A3.4 Class 1** 系统结构须为：单通道带功能测试（A5.5）**或** 单通道带周期自检（A5.6）
- **A3.5 Class 2** 系统结构须为：单通道带周期自检与监测（A5.7）**或** 双通道同构比较（A5.3）**或** 双通道异构比较（A5.2）
- **A3.11** 故障/错误须在导致风险前被检出
- **Table A2.1** 给出各微电子部件（CPU、内存、外部通信、IO 等）失效模式的覆盖措施示例，按 SW Class 1 / 2 标注 "rq"（required）[1]
